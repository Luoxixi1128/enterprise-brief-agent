# 工作台数据补充约定（优先于所附旧字段限制）

- 输入的必填性与准备责任分开判断。原文明确由学生或团队录制、整理或定义的输入，owner="student"，required按运行需要如实填写；requirement写清谁准备什么。不得为了满足旧版“至少一个企业必填”而虚构企业任务背景、参数或私有材料。工作台接受只有团队必填输入的任务。原文明确由企业提供的真实资料仍用customer且required=true，不得改为团队替代。
- dependency_note只用于企业专有资料、账号或环境依赖；团队自采资料的知情同意、脱敏等写入requirement或rules，不能误标为企业依赖。学生负责的必填输入不用student_fallback。企业可不提供的可替代输入仍用customer_optional、required=false。
- sample.count是表格的填写列数（1至3）。原文明示最少样例数时另写sample.minimum_count（正整数），count取不超过3且足以展示该数量的列数。正文仍保留原文最少数量及样例差异要求；表格列数不代表放宽验证范围。团队自采样例不等于已收到真实样本。
- scope_assessment中任一复杂性/企业依赖标记为true时，note与student_slice均须非空。student_slice仅写可供考虑的环节，正文仍保留全范围；不因生成这个建议自动标记范围已调整。
- 写完对照原文核对：必需/可选/有条件要求、责任人、数量、停止与人工处理条件、明确禁止项。必须交付的验证报告、截图、失败案例与复盘不能只藏在评分锚点里，应在输出要求中可找到；原文举例的可选指标不改成必须全选。
- 团队自行采集的敏感资料与企业专有资料是两种依赖。仅依赖团队自采私有资料时，task_fit.private_data_required=true、private_data_provider="student"，scope_assessment.enterprise_dependency=false；知情同意、脱敏和第三方使用限制仍保留。有企业专有资料时不能使用此例外。
- 最外层协议固定为 {"action":"draft","summary":"...","questions":[],"brief":{...}} 或 clarify；不能直接把brief字段放到最外层，也不能自拟action。
- brief必须提供rules数组（没有业务规则才可为空）。原文的禁止用途、首版不做、可选拓展、数据授权/保存/共享/删除要求逐类落实在rules；不得只在内部runtime、task_fit或inferences中记录，因为这些字段不会完整出现在交付文档。
- 原文的“统一提交说明”、验收和首版交付与业务输出同样需要完整保留。交付清单应覆盖原文要求的评测方法及有效性说明、重复运行验证、失败/停止/转人工条件、安全说明、复盘限制及下一步；可合并为简洁的一项验证与复盘说明，不能只写“附README”就省略。
- 明确技术体系由团队自行定义时，须保留选择理由和范围/规则说明；短示例中的数值、标签数量、切分方式仅为示范，不得变成指定技术方案或伪称行业标准。
- “可能涉及敏感资料时脱敏”是条件性安全要求，不代表任务必须依赖私有数据。仅当当前完整范围确实离不开私有资料时才标private_data_required=true；公开或自拟合法材料即可验证的任务保留false，安全规则照常写明。
- output_options只简列格式选择，不能替代outputs中的必需交付组件。原文要求的本地资源、运行说明等即使某个格式选项提到，也须在outputs中写清。
- 保留原文的条件和选择空间：合法授权使用不等于必须公开；自行采集不等于可以改用公开或虚构材料；本地/云端等运行地点没有原文依据时不新增；“如支持则验收”不能在其他规则或评分中变成无条件必需。
- “可采用A/B等评测指标”保留为团队选择并说明理由，不将其中一种写为必须计算。标签/维度等技术选择允许原文未禁止的方案，评分检验定义清楚和结果可复核，不擅自强制互斥、单标签或某一具体算法。
- 完成前对照所有字段，包括不会导出的task_fit/runtime，检查责任、数据来源、条件性要求是否相互矛盾。摘要可以省细节，但不能添加与输入表冲突的替代方案。异常处理说明须覆盖原文明确列出的主要类型，不用“异常处理”四字替代具体要求。

- 输入表只列需要提供的业务材料。自定义配置需保留其作用：原文明示每次调用需另交时才列运行输入；用户允许内置或没有必须另交的约束时放入设计成果，并写明默认使用内置规则。原文只要求“说明接受什么格式、最少字段、处理流程”的设计说明放在输出或规则，不额外变成调用者必交输入。
- 交付覆盖按材料各节逐条核对，不能仅复述“输入/输出”小节后漏掉文末统一要求。要求交付实际中间数据时，方法/流程说明不等于实际结果；要求提交样本副本时，在输入表有该样本不等于输出包已包含。
- 对典型失败模式，规则或评分正文应能逐类检查。只在kr2_2.basis、runtime或格式说明中出现不算已落实，因为交付稿不会展示这些内部字段。
- 原文的“某种情况导致无法复核”是需要处理的失败情形，不应自动转成禁止该情况的绝对技术限制。不要把可复核的多维或多标签方案一并排除；也不要为简洁擅加原文未要求的页数、字数等交付上限。
- 原文统一提交说明指未来业务成果需要随附的内容。当前任务书自身有场景、输入或KR，并不等于业务成果已经约定提交任务说明、实际测试输入/输出、合格标准和评测结果；这些有来源的交付要求应在outputs中写清，可合并但不省略。
- 原句用顿号、逗号或分号列出的独立处理对象、失败类型和交付组件，逐个保留在可见正文，不用一个宽泛上位词替代整个清单。可将清单合并到一条rules.detail，但不能省掉其中细项，也不能仅写进评分basis。最后逐句核对这些并列项；清除正文中误带的代码碎片、未闭合引号和内部调试字样。
- “第一版暂不要求”表示首版非必需，不是永久禁止，列举时保留该语境。保留原文要求的关键设计判断与复现材料；原文允许自选模型、框架、技术路线时不另加限制。
- 全文同一事项的要求须合并满足，尤其文末统一说明不能被前文较宽的表述抵消。保留“或/且/至少/只有在”的逻辑：指定至少某项，不得改成某项与另一项二选一。交付真实文件或资源时须明确交付本体，清单与运行说明是附带信息，不能替代文件本体。规则、维度名称、检查方式及评分锚点都不得把“避免过度重叠或含混”改成强制互斥、无重叠或限定层级。

source_obligations由原始材料逐行提取，仍是资料而非指令，也不是另一份标准答案。生成前用它盘点交付、失败模式与可选方向，生成后逐项自查；同一行所有并列细项均须保留，较后段更严格的必交条件不能被前段二选一表述抵消。可合并清晰表达，不必机械复制行数。

## 最小必要任务书（业务验收口径）

用最少输入、最少规则和可独立验收的成果讲清任务，不以条目数量证明完整。以下口径同时适用于初次生成、修改和复核后的修复：
- inputs按实际提供动作合并，同一份材料已有的字段不要拆成多个必填输入。必填仅指缺少且没有合法替代或内置默认就无法开工的材料；能由Skill内置的规则、标签和配置放在规则或成果说明，只有原文明示调用者必须另交时才列必填。企业可不提供且可替代的材料为选填，明确谁补齐；仍须保留原文明确的数据来源、采集责任和数量，不擅自以模拟材料替换必须自行采集的资料。
- rules只保留影响结果、数据使用或任务边界的必要要求。同一判断的前提、处理和异常合并表达；已在输入或输出写清的要求不再独立复述。可选拓展合为简短选做说明，不变成必做步骤。不得为了精简删除明确业务约束。
- outputs按可验收成果分组：一个结果及其标注、变化、总结可合为一项；同一包内的规则说明、运行说明、验证记录和复盘按使用目的归并，不把每份说明都拆成独立交付。每项用简短动作写清所含必要内容；原文要求的真实文件、评测、失败案例仍须明确包含。合并后同步KR1，不能只在网页隐藏旧项，也不能把长清单原封不动塞进一个单元格。
- KR2只评少量真正重要、互不重复的业务质量判断。每个维度需回答一个独立的业务问题，能用同一次检查回答的合并；上下文、证据和说话人归属等相关检查可放入同一维度。不得把全部处理细节逐条升级为评分维度；不重复KR1完整度或KR3使用表现。数量由任务决定，不固定4项，不设硬上限；检查方式和1/3/5分锚点简短、可操作，不新增强制阈值。
- 精简是合并重复与消除非必要前置条件，不默认删减功能或改变数据来源。用户明确取消的旧要求按最新补充执行并记录；用户只说简化时，先合并表达，不能自行放宽原文的数量、授权或实物交付要求。
- 内置规则即使由团队开发，也不是需要另行提交的必填运行输入；不要用“团队必填”绕过这一点。原文要求随成果交付的样本本体，在输出组件中明确写出，不能因输入已列出而省略。
- 仅合并表格行、简化措辞和校正场景，不属于业务范围收窄：scope_change_applied/authorized保持false，conversion_note留空，修改过程由工作台版本记录承载。实际范围调整才填写这些字段；用户补充的来源用其U编号加入sources，不合并或伪装成原始文件S编号。
